### 3.10 Operator signup (NEW v1.4 — P13)

Operator self-service signup. Creates `User` + `Operator` + `OperatorUser` + 2 consent records in **one transaction**. Emits `operator:applied` WS event to `admin:notifications` **after** transaction commit. Writes audit row.

**Request:**
```
POST /v1/operator/auth/signup
Content-Type: application/json

{
  "companyName": "Sharma Travels Pvt Ltd",
  "gstin": "09AAACH7409R1ZZ",
  "pan": "AAACH7409R",
  "email": "founder@sharmatravels.com",
  "phone": "+919876543210",
  "password": "SecurePass123!"
}
```

**Request schema (`.strict()`):**

| Field | Type | Validation |
|---|---|---|
| `companyName` | string | 2–200 chars |
| `gstin` | string | 15-char regex `^[0-9]{2}[A-Z]{5}[0-9]{4}[A-Z]{1}[1-9A-Z]{1}Z[0-9A-Z]{1}$` |
| `pan` | string | 10-char regex `^[A-Z]{5}[0-9]{4}[A-Z]{1}$` |
| `email` | string | valid email, lowercased server-side |
| `phone` | string | E.164 (per §2.4) |
| `password` | string | 12–128 chars, must include letter + digit (Argon2id-hashed) |

**Response (201):**
```json
{
  "data": {
    "operatorId": "uuid",
    "userId": "uuid",
    "status": "APPLIED",
    "message": "Application submitted. You will be notified when your account is approved."
  },
  "meta": {
    "requestId": "req_abc123"
  }
}
```

**Rules:**

- Pre-check (all in one query): `findOperatorByGstin` for duplicate; `users` for duplicate email; `users` for duplicate phone.
- All 4 writes (`User`, `Operator` with `status: 'APPLIED'`, `OperatorUser` with `role: 'OWNER'`, 2 `consent_records`) happen inside **one** `prisma.$transaction`.
- Password hashed with Argon2id before `OperatorUser` insert.
- Audit row: `action: 'operator_signup'`, `reason: 'Self-signup via /operator/auth/signup'`, `actorUserId: <new user>`.
- WS emit: `emitToTopic('admin:notifications', events.operatorApplied(...))` — fires **after** tx commit (per §2.4 non-negotiable "Emit AFTER tx commit").
- On any step failure, whole tx rolls back. Unique constraint on GSTIN at commit time is the final race guard.

**Errors:**

| Error | HTTP | When |
|---|---|---|
| `INVALID_GSTIN_FORMAT` | 400 | GSTIN fails regex — **new v1.4 code** |
| `INVALID_PAN_FORMAT` | 400 | PAN fails regex — **new v1.4 code** |
| `INVALID_PHONE_FORMAT` | 400 | Phone not E.164 |
| `INVALID_EMAIL_FORMAT` | 400 | Email malformed |
| `VALIDATION_ERROR` | 422 | Password too weak, `companyName` out of bounds, or extra field (`.strict()`) |
| `EMAIL_ALREADY_REGISTERED` | 409 | Email exists |
| `PHONE_ALREADY_REGISTERED` | 409 | Phone exists |
| `GSTIN_ALREADY_REGISTERED` | 409 | GSTIN exists (existing error code) |
| `RATE_LIMITED` | 429 | >3 requests / 10 min / IP |

**No `emailVerified` gate at signup.** The `users` row is created with `emailVerified: false`. Operator cannot log in via `/operator/auth/login` until admin approves and email is verified — that's a separate flow. The signup response does **not** issue tokens.

### 5.3 Bus registration flow (EXPANDED v1.3)

**Diagram: Bus registration sequence**
*Two phases — operator registers (PENDING), admin approves. `busType` + `amenities` set at registration; required for search filtering.*

```mermaid
sequenceDiagram
    actor O as Operator
    actor A as Admin
    participant API as API
    participant DB as DB

    O->>API: POST /operator/buses { registrationNumber, model, capacity, busType, amenities }
    API->>DB: INSERT buses (approval_status=PENDING, bus_type, amenities_json)
    API-->>O: { busId, status: "PENDING", busType, amenities }

    O->>API: PUT /operator/buses/:id/layout { rowsCount, columnsCount, seats[] }
    API->>DB: INSERT seat_layouts, seats
    API-->>O: { layoutId, seats, aisleCells }

    A->>API: GET /admin/buses?status=PENDING
    A->>API: POST /admin/buses/:id/approve
    API->>DB: UPDATE buses SET approval_status=APPROVED
    API-->>A: { approved }
    Note over O,DB: Bus now searchable
```

**Create bus request:**
```json
{
  "registrationNumber": "DL01AB1234",
  "model": "Volvo 9400",

  "insuranceDocRef": "r2://uploads/insurance-xyz.pdf",
  "insuranceExpiresAt": "2027-06-30"
}
```

`busType` ∈ `SEATER` | `AC_SEATER` | `SLEEPER` | `AC_SLEEPER` | `SEMI_SLEEPER`. `amenities`: string array, max 20, each 1–50 chars.

### 5.11 Operator trip cancel (NEW v1.4 — P12)

**`POST /v1/operator/trips/:id/cancel`**

Operator-initiated cancellation of an entire trip. Triggers cascade refunds for every CONFIRMED booking on the trip. Per-booking cascade failure is **non-fatal** (per §2.4 non-negotiable) — the trip is cancelled even if 1+ refunds fail; failures are logged + retried by `webhook-replay.worker`.

**Request:**
```json
{
  "reason": "BUS_BREAKDOWN",
  "notes": "Engine failure before departure"
}
```

`reason` ∈ `BUS_BREAKDOWN` | `OPERATOR_ISSUE` | `WEATHER` | `GOVERNMENT_RESTRICTION` | `OTHER`. `notes` optional, 0–500 chars.

**Response (200):**
```json
{
  "data": {
    "tripId": "uuid",
    "status": "CANCELLED",
    "cancelledAt": "2026-10-27T21:00:00.000Z",
    "cancellationReason": "BUS_BREAKDOWN",
    "bookingsCancelled": 12,
    "refundsInitiated": 12,
    "refundFailures": 0,
    "totalRefundPaise": 585000
  }
}
```

**Rules:**

- Pre-conditions: trip status ∈ `SCHEDULED` | `IN_PROGRESS`; if `COMPLETED` or `CANCELLED` → `400 TRIP_NOT_CANCELLABLE`.
- All affected bookings transition to `CANCELLED` with `refund_tier: 'TIER_FULL'` (per §4.5 — operator-cancel always full).
- Each booking's refund is `INITIATED` — actual processing via Razorpay per §13 webhook flow.
- Cascade per booking wrapped in try/catch; one failure does not abort the rest. Failures counted in `refundFailures` and retried asynchronously.
- Emits `trip:cancelled` to `trip:live:{tripId}` (per §8.7).
- Emits `booking:cancelled` + `refund:requested` per affected booking (per §8.7).
- Audit row per booking + one aggregate audit row for the trip cancel itself.
- Cross-tenant → `404`.
- **WS emit AFTER tx commit** (per §2.4).

### 1.5 The producer-only pattern

**Diagram: Producer-only vs publisher-subscriber surfaces**
*Three surfaces interact with the event stream. BusVerse is subscriber-only. BusCon web is subscriber-only. Operator App is producer-only — it POSTs GPS samples and boarding scans that trigger events, but never subscribes.*

```mermaid
flowchart LR
    subgraph PRODUCE["Producers"]
        OA["Operator App<br/>(POST /gps, /scan)"]
        API["API<br/>(webhooks, cron, handlers)"]
    end

    subgraph BUS["Event bus"]
        WS["WebSocket<br/>4 topics"]
    end

    subgraph CONSUME["Subscribers"]
        BV["BusVerse"]
        BC["BusCon web"]
    end

    OA --> API
    API --> WS
    WS --> BV
    WS --> BC
```

**Rules:**

| Surface | Producer | Subscriber |
|---|:---:|:---:|
| BusVerse | — (client) | ✅ |
| BusCon web | — (client) | ✅ |
| Operator App | ✅ (POST /gps, /scan, /trips/:id/start, etc.) | ❌ **never subscribes** |
| API | ✅ (webhooks, crons, handlers) | — |

**Rationale:** The Operator App is a driver's field tool. Subscribing to events would require driver-initiated polling loops on a mobile device — battery cost, bandwidth cost, and no value because the driver already knows what's happening (they just did it). If a driver needs current state, they POST and the response has it. Phase 2 could add a driver notification subscription (`driver:notifications` topic) if push notifications demand it.

|---|:---:|:---:|:---:|

**Notes:**

| Note | Detail |
|---|---|
| "Any user viewing" | Even anonymous visitors can subscribe to `seat:availability` for a schedule (public topic) |

| Operator App | Producer-only — no subscription code in the app |

### 2.4 Why Operator App doesn't subscribe

| Reason | Detail |
|---|---|
| **No value** | The driver already knows what's happening — they just triggered it |
| **Battery cost** | Background WS connection drains battery |
| **Bandwidth cost** | Continuous WS traffic on mobile data |
| **Already handled** | `POST /gps` returns 200; `POST /scan` returns result; trip state is in `GET /trips` |
| **Phase 2 plan** | Driver push notifications use FCM (per `buscon/00` §17.2), not WS |

**Rule:** Operator App never opens a WebSocket connection in Phase 1. Any future subscription (Phase 2+) becomes a new topic (`driver:notifications`) and a new amendment to SH-04.

## 3. Topic Reference

### 3.1 `seat:availability:{scheduleId}`

**Diagram: Seat availability flow**
*Three events drive the seat deck. Every user viewing the schedule subscribes. Events emit within 100ms of DB commit.*

```mermaid

    Note over API,BV: Booking confirmed
    API->>WS: seat:booked
    WS-->>BV: { seatId, bookingId }
```

**Events:** `seat:locked`, `seat:released`, `seat:booked`

### 4.3 Event versioning (resolves G4)

**Rule:** Every `data` object carries `_v: 1` in Phase 1.

| Change | `_v` bump? |
|---|---|
| Add new field | ❌ (additive) |

| Rename field | ✅ → `_v: 2` |
| Change field type | ✅ → `_v: 2` |
| Change semantics | ✅ → `_v: 2` |

**Client behavior:**

| `_v` value | Client action |
|---|---|
| `1` | Accept |
| `2+` (unknown) | Log warning; ignore event; don't crash |
| Missing | Treat as `1` (defensive) |
| Non-integer | Reject; log error |

**Server behavior:** Server emits `_v: 1` for the entire Phase 1 lifetime. Phase 2 can introduce `_v: 2` per event; clients upgraded in a coordinated release.

### 4.4 Field naming and format

**Inherited from `07` v1.2 §2.4 (data type glossary):**

| Format | Example |
|---|---|
| camelCase | `seatId`, `bookingId`, `lockedUntil` |
| ISO 8601 UTC | `"2026-10-25T14:32:00.000Z"` |
| Money | `amountPaise: 48750` (integer paise) |
| Enums | `SCREAMING_SNAKE` |
| IDs | UUID (opaque to client) |
| Null | `null` (never absent) |

### 4.5 The `_v: 1` addition (Amendment A1)

**Current state:** `07` v1.2 §8.7 shows `data` payloads **without** `_v`.

**Required:** `07` v1.3 §8.7 must add `_v: 1` to every payload. This is a **non-breaking additive change** — clients that ignore extra fields already handle it; clients that validate strictly need updating.

**Amendment:** A1 (Medium priority, Wave 2).

## 5. Delivery Guarantees

### 5.1 WS delivery model

**Diagram: Delivery guarantees**
*Three layers with different guarantees. WebSocket is at-most-once per connection. Module event bus is at-least-once. Polling fallback is at-least-once (per-poll).*

```mermaid
flowchart LR
    MOD["Module event bus<br/>at-least-once"]
    WS["WebSocket<br/>at-most-once"]
    POLL["Polling fallback<br/>at-least-once"]

    MOD -->|"publisher"| WS
    WS -->|"if fails"| POLL

    MOD --> GUAR["Every subscriber sees event (may duplicate)"]
    WS --> GUAR2["Best-effort delivery (may drop)"]
    POLL --> GUAR3["Eventually consistent (poll catches up)"]
```

### 5.2 Delivery guarantees by layer

| Layer | Delivery | Ordering | Failure mode |
|---|---|---|---|
| Module event bus (in-process) | At-least-once | Per-entity | Retry via BullMQ |
| WebSocket broadcast | **At-most-once per connection** | Per-entity within one connection | Event dropped; client must poll to recover |
| Polling fallback | At-least-once per poll | N/A | Repeats until success |

**Rationale for WS at-most-once:** Real-time events are ephemeral. If delivery fails (network drop, socket closed), the client recovers via polling — not by retry storming the WS server. This matches industry practice (Kafka at-least-once for persistence, WS at-most-once for UI).

### 5.3 Idempotency requirements per event

**Diagram: Idempotency matrix**
*Every event has an idempotency rule. Some are naturally idempotent (SET-based state). Others require explicit dedup (based on a unique field).*

```mermaid
flowchart TB
    IDEM["Idempotency per event"]

    IDEM --> NAT["Naturally idempotent<br/>(SET-based state)"]
    IDEM --> DEDUP["Requires dedup<br/>(append-based state)"]

    NAT --> N1["seat:locked → set MINE"]
    NAT --> N2["seat:released → set AVAILABLE"]
    NAT --> N3["seat:booked → set BOOKED"]
    NAT --> N4["bus:position → set position"]
    NAT --> N5["trip:started/ended/cancelled → set state"]

    DEDUP --> D1["booking:confirmed → check ticketId"]
    DEDUP --> D2["boarding:verified → check boardedAt"]
    DEDUP --> D3["payment:succeeded → check paymentId"]
```

**Per-event idempotency rules:**

| Event | Idempotency requirement |
|---|---|
| `seat:locked` | SET seat state to MINE/LOCKED (naturally idempotent) |
| `seat:released` | SET seat state to AVAILABLE (naturally idempotent) |
| `seat:booked` | SET seat state to BOOKED (naturally idempotent) |
| `bus:position` | SET position to latest (naturally idempotent) |
| `trip:started` | SET trip state to IN_PROGRESS (idempotent) |
| `trip:delayed` | SET delay reason + minutes (idempotent) |
| `trip:ended` | SET trip state to COMPLETED (idempotent) |
| `trip:cancelled` | SET trip state to CANCELLED (idempotent) |
| `booking:confirmed` | Dedup on `ticketId` — only apply if different from last |
| `booking:cancelled` | SET state to CANCELLED (idempotent) |
| `booking:expired` | SET state to EXPIRED (idempotent) |
| `boarding:verified` | Dedup on `boardedAt` — only apply if newer than last |
| `payment:succeeded` | Dedup on `paymentId` — only apply if new |
| `operator:applied` | Dedup on `operatorId` |
| `refund:requested` | Dedup on `refundId` |
| `gps_anomaly` | Dedup on `detectedAt` |

**Client rule:** For dedup events, maintain a small set of last-seen IDs (per topic). Discard duplicates. Set size bounded to 100 (FIFO).

### 5.4 Ordering guarantees

| Scope | Ordering |
|---|---|
| Per-entity (same seat, same trip, same booking) | ✅ Guaranteed within one connection |
| Per-entity (across reconnection) | ❌ Not guaranteed; client must re-fetch state |
| Cross-entity | ❌ Not guaranteed |

**Client rule:** If `event.ts` is older than last-seen `ts` for this entity, drop event (out-of-order safety).

**Reference:** `busverse/04` §11.6 (out-of-order `bus:position` handling).

### 6.1 Topic authorization matrix

|---|---|---|

### 6.2 Authorization check per subscription

**Diagram: Authorization flow on subscribe**
*When a client subscribes to a topic, the server validates the token and the authorization rule. Failed authorization closes the connection (not just the subscription).*

```mermaid
sequenceDiagram

    participant WS as WebSocket server
    participant API as API (auth check)

            WS-->>C: subscribed
        else Forbidden
            API-->>WS: 403
            WS-->>C: close 1008
        end
    end
```

| Limit | Value |
|---|---|

| Max messages per session | 60 / min |
| Max connections per user | 5 |

## 7. Reconnection & Backoff

### 7.1 Reconnection state machine

**Diagram: Reconnection state machine**
*Five states with explicit transitions. Backoff schedule is exponential with a max of 5 retries, then falls back to polling.*

```mermaid
stateDiagram-v2
    [*] --> Disconnected
    Disconnected --> Connecting: connect()
    Connecting --> Connected: auth OK
    Connecting --> Reconnecting: fail (attempt++)
    Connected --> Reconnecting: disconnect
    Reconnecting --> Connecting: wait backoff
    Reconnecting --> Polling: 5 retries exhausted
    Polling --> Connecting: retry every 60s
    Connected --> [*]: user closes
```

### 7.2 Backoff schedule (resolves N3)

**Diagram: Backoff sequence**
*Exponential backoff from 1s to 16s across 5 retries. On 6th failure, switch to polling.*

```mermaid
flowchart LR
    A1["Attempt 1<br/>wait 1s"] --> A2["Attempt 2<br/>wait 2s"]
    A2 --> A3["Attempt 3<br/>wait 4s"]
    A3 --> A4["Attempt 4<br/>wait 8s"]
    A4 --> A5["Attempt 5<br/>wait 16s"]
    A5 --> POLL["Switch to polling<br/>(WS retry every 60s)"]
```

| Attempt | Delay before retry | Cumulative time |
|---:|---:|---:|
| 1 | 1s | 1s |
| 2 | 2s | 3s |
| 3 | 4s | 7s |
| 4 | 8s | 15s |
| 5 | 16s | 31s |
| 6+ | — (polling) | — |

**Rule:** Backoff resets on successful connection. If a connection stays up > 30s, next disconnect starts from attempt 1.

### 7.3 Re-authentication on expiry

**Reference:** `07` v1.2 §8.5, `09` v1.2 §12.5.6.

**Diagram: Token refresh during WS**
*Server sends `auth:expiring` 60s before JWT expiry. Client sends `auth:refresh` within 30s. On success, connection continues. On fail, close and reconnect.*

```mermaid
sequenceDiagram
    participant C as Client
    participant WS as Server

    Note over WS: 60s before JWT expiry
    WS->>C: auth:expiring
    C->>C: POST /auth/refresh
    C->>WS: { action: "auth:refresh", refreshToken }
    WS->>WS: Validate + rotate
    WS-->>C: auth:refreshed
    Note over C,WS: Connection continues

    Note over C,WS: If client misses 30s window
    WS->>C: close 4001 (token expired)
    C->>C: Reconnect with fresh token
```

**Rules:**

| Aspect | Detail |
|---|---|
| `auth:expiring` timing | 60s before JWT `exp` |
| Client response window | 30s |
| Missing window | Server closes with 4001 |
| Refresh failure | Client re-authenticates via login |

**Reference:** `08` v1.1 WF-R-03.

### 7.4 Reconnect state recovery

**Diagram: State recovery on reconnect**
*After reconnection, client must re-fetch state (not rely on missed events). Different endpoints for different topics.*

```mermaid
flowchart LR
    RECON["Reconnect success"] --> REFETCH["Refetch current state"]
    REFETCH --> S1["seat:availability → GET /schedules/:id/availability"]
    REFETCH --> S2["trip:live → GET /trips/:id/live"]
    REFETCH --> S3["booking → GET /bookings/:id"]
```

**Rule:** Never trust the event stream alone to reconstruct state. On reconnect, refetch. Events only update state going forward.

**Reference:** `busverse/02` §15.3 (polling recovery), `busverse/04` §11.4.

## 8. Polling Fallbacks

### 8.1 Canonical intervals (resolves G3)

**Diagram: Polling fallback per topic**
*Three fallback intervals. All start only after WS reconnect fails 5 times. Manual retry every 60s.*

```mermaid
flowchart LR
    WS["WS disconnect"] --> R["5 retries failed"]
    R --> P1["seat:availability<br/>poll every 3s"]
    R --> P2["trip:live<br/>poll every 3s"]
    R --> P3["booking<br/>poll every 5s"]
    P1 -.->|"retry WS every 60s"| WS
    P2 -.->|"retry WS every 60s"| WS
    P3 -.->|"retry WS every 60s"| WS
```

### 8.2 Fallback endpoint map

| Topic | Fallback endpoint | Interval | Source |
|---|---|---|---|
| `seat:availability:{scheduleId}` | `GET /schedules/:id/availability` | **3s** | `busverse/02` §15.1 |
| `trip:live:{tripId}` | `GET /trips/:id/live` | **3s** | `busverse/04` §11.4 |
| `booking:{bookingId}` | `GET /bookings/:id` (or `/payments/:id`) | **5s** | `busverse/04` §11.4 |
| `admin:notifications` | N/A — no Phase 1 client | — | — |

### 8.3 Fallback lifecycle

**Diagram: Polling lifecycle**
*Polling starts on WS failure, runs at canonical interval, stops on WS reconnect.*

```mermaid
stateDiagram-v2

    Polling --> Polling: poll every 3-5s
```

## 9. GPS Broadcast Throttle Resolution (resolves G1)

### 9.1 The contradiction

**Diagram: The current ambiguity**
*Three docs describe different rates. `02` says 5s client. `07` says 3s broadcast. Nothing says how they interact.*

```mermaid
flowchart LR
    D02["02 §6.6<br/>client sends 5s"]
    D07["07 §8.7<br/>'throttled to 3s'"]
    D09["09 §8.4<br/>5s cadence"]

    D02 --> AMBIG["Ambiguous<br/>3s and 5s?"]
    D07 --> AMBIG
    D09 --> AMBIG
```

### 9.2 The resolution

**Rule:** The 3s value in `07` v1.2 §8.7 is a **defensive floor**, not the target rate.

| Layer | Rate | Purpose |
|---|---|---|
| Client sends | Every 5s | Per `02` §6.6 |
| Server stores (Redis) | Every 5s | Per FR-OP-010 |
| Server stores (Postgres) | Every 30s | Per FR-OP-010 |
| Server broadcasts | Every sample received **unless** two arrive <3s apart | Defensive floor against rogue clients |
| Client display | Interpolated between samples | Per `busverse/04` §10.4 |

### 9.3 When the 3s floor triggers

**Diagram: Throttle trigger**
*With normal 5s cadence, the floor never triggers. Only if a malicious client sends >3s frequency does the server discard.*

```mermaid
flowchart LR
    A["Sample 1<br/>t=0"] --> B["Sample 2<br/>t=5s<br/>Δ=5s > 3s → emit"]
    B --> C["Sample 3<br/>t=10s<br/>Δ=5s > 3s → emit"]

    M1["Malicious sample 1<br/>t=0"] --> M2["Malicious sample 2<br/>t=1s<br/>Δ=1s < 3s → discard"]
    M2 --> M3["Malicious sample 3<br/>t=2s<br/>Δ=1s < 3s → discard"]
```

**Rules:**

| Scenario | Behavior |
|---|---|
| Normal client (5s cadence) | Every sample emitted |
| Slow client (>5s cadence) | Every sample emitted |
| Rogue client (<3s cadence) | Extra samples discarded; only first of each 3s window emitted |
| Burst from one client | Server applies floor per `trip_id` (not per connection) |

### 9.4 Why 3s floor

| Reason | Detail |
|---|---|
| **Passenger UX** | 3s updates are smooth enough; 1s is overkill |
| **Bandwidth** | Reduces broadcast fan-out to ~600 samples/hour per trip |
| **Abuse prevention** | Blocks malicious clients spamming 100s/sec |
| **No impact on normal use** | Normal 5s cadence is safely above the floor |

### 9.5 Amendment

**A2 (Medium, Wave 2):** `07` v1.3 §8.7 must clarify: "server broadcasts every sample unless two arrive <3s apart (defensive floor against rogue clients; normal 5s cadence never triggers this)".

### 10.1 Ordering guarantees

**Diagram: Ordering per scope**
*Within one WS connection: per-entity ordering guaranteed. Across connections or entities: not guaranteed. Client must handle.*

```mermaid
flowchart TB
    ENT["Per-entity within connection<br/>✅ Guaranteed"]

    ENT --> OK1["seat:A1 events in order"]
```

### 10.2 Client-side ordering safety

| Rule | Detail |
|---|---|
| Compare `ts` field | Drop events with `ts` older than last-seen |
| Per-entity tracking | Maintain last-seen `ts` per entity ID |
| Reconnect refetch | After reconnect, refetch state (see §7.4) |

### 10.3 Server-side ordering safety

| Rule | Detail |
|---|---|
| Emit after commit | Never emit before DB transaction commits |
| Same entity = same queue | Per-entity publish queue ensures order |
| Cross-entity = no order | Independent publish |

**Rule:** The server does not buffer or reorder events. If two events for the same entity arrive, the DB order determines the emit order.

## 11. Failure Modes

### 11.1 Failure matrix

**Diagram: Failure routing**
*Four failure types across the WS pipeline. Each has a defined recovery.*

```mermaid
flowchart TB
    F["Failure"]

    F --> WS["WS connection lost"]
    F --> AUTH["Auth expired"]
    F --> RATE["Rate limited"]
    F --> SERVER["Server error"]

    WS --> R1["Reconnect with backoff<br/>Fallback to polling"]
    AUTH --> R2["Refresh + re-auth<br/>else force logout"]
    RATE --> R3["Backoff per Retry-After"]
    SERVER --> R4["Reconnect with backoff"]
```

### 11.2 Failure behavior table

| Failure | Detection | Client behavior | Server behavior |
|---|---|---|---|
| WS connection lost | Socket close | Reconnect with backoff (§7.2) | Log; allow reconnect |
| Auth expired | 4001 close code | Refresh token; reconnect | Send `auth:expiring` at 60s before |
| Rate limited | 429 message | Backoff per Retry-After header | Enforce per `09` §12.5 |
| Server error (500) | Error message | Reconnect with backoff | Log + alert |
| Too many reconnects | 401 TOO_MANY_RECONNECTS | Wait 60s before retry | Enforce per §6.6 |
| Message size > 64KB | Error message | Log; don't retry | Enforce per §6.5 |
| Origin mismatch | 1008 close | Fail silently (misconfigured) | Log SECURITY event |
| Malformed message | 1008 close | Log error; don't retry | Log + count metric |

### 11.3 Redis pub/sub (Phase 2) failure

**Not Phase 1.** When Phase 2 adds multi-instance WS via Redis pub/sub:

| Failure | Behavior |
|---|---|
| Redis pub/sub down | WS connections continue; broadcast deferred; clients fall to polling |
| Partial Redis (some channels) | Depends on channel isolation |

**Phase 1:** Single WS instance — no Redis pub/sub needed (per `03` v1.2 §14.3).

### 11.4 Graceful degradation

**Diagram: Degradation ladder**
*WS → polling is the fallback. If polling fails, manual refresh. Three-tier degradation.*

```mermaid
flowchart LR
    L1["Tier 1<br/>WebSocket<br/>(best UX)"]
    L2["Tier 2<br/>Polling<br/>(slower, complete)"]
    L3["Tier 3<br/>Manual refresh<br/>(user-driven)"]

    L1 -->|"WS fails"| L2
    L2 -->|"polls fail"| L3
    L3 -.->|"network recovers"| L1
```

**Rule:** Never show a "stuck" state. The user can always manually refresh. Show clear status indicators per §8.4.

## 18. Summary

**`shared/04-EVENT-AND-REALTIME-CATALOG.md` is the canonical catalog of every real-time event in the system — 4 WebSocket topics, 16 events, their payload schemas, subscriber matrix, authorization rules, delivery guarantees, reconnection behavior, and polling fallbacks. This is the fourth consolidation contract in the `shared/` folder** (after SH-00 portal, SH-02 QR payload, SH-03 seat lock lifecycle). It resolves three material findings: **(G1) the GPS broadcast throttle contradiction** — `07` v1.2 §8.7 says "throttled to 3s" but the actual cadence is 5s; the 3s value is a **defensive floor** against rogue clients, not the target rate; resolved in §9. **(G2) `admin:notifications` Phase 1 reality** — events are emitted to the topic but no Phase 1 client subscribes (no admin WS UI); events land in `audit_logs` for review via `buscon/01` §12; Phase 2 adds the UI without changing emission behavior; resolved in §6.4. **(G4) event versioning** — every `data` payload includes `_v: 1`; additive changes don't bump; removing/renaming/type-changing bumps to `_v: 2`; clients reject unknown `_v` with a warning, not a crash; resolved in §4.3.

**The subscriber matrix (§2.2) is the hero diagram**: `seat:availability:*` → BusVerse only; `trip:live:*` → BusVerse + BusCon web; `booking:*` → BusVerse only; `admin:notifications` → **Phase 2 UI** (Phase 1 no subscriber). **Operator App is producer-only** (§1.5) — it POSTs GPS samples, boarding scans, and trip lifecycle actions that trigger events, but never opens a WebSocket connection. This resolves an ambiguity in `07` v1.2 §8.1 which implied all surfaces subscribe.

**The 16 canonical events** span 4 topics — 3 seat events (`seat:locked`, `seat:released`, `seat:booked`), 5 trip events (`bus:position`, `trip:started`, `trip:delayed`, `trip:ended`, `trip:cancelled`), 5 booking events (`booking:confirmed`, `booking:cancelled`, `booking:expired`, `boarding:verified`, `payment:succeeded`), 3 admin events (`operator:applied`, `refund:requested`, `gps_anomaly`). Each has a full JSON payload schema with `_v: 1`. **Two events are new or repaired:** `seat:locked` gains `lockedByMe` (was in `busverse/02` §12.3 but missing from `07` §8.7), and `gps_anomaly` is formalized as the 16th event (was referenced in `buscon/04` §10.5 but never made canonical). **`bus:position`** has the full 11-field payload — `tripId, scheduleId, lat, lng, speedKmh, bearing (null Phase 1), accuracyM, recordedAt, receivedAt, nextStandId, etaMinutes` — which was only partial in `07` v1.2 §8.7. **`boarding:verified`** carries the multi-passenger extension `passengerCount` + `allSeatLabels[]` matching `buscon/05` §13.2's A3 amendment.

**Delivery guarantees (§5)** distinguish three layers: module event bus at-least-once (BullMQ retry), WebSocket at-most-once per connection (drop tolerated, client polls to recover), polling at-least-once per poll. **Idempotency per event (§5.3)** splits into naturally-idempotent events (SET-based state — `seat:locked`, `bus:position`, `trip:started`, etc.) and dedup-required events (append-based state — `booking:confirmed` dedup on `ticketId`, `boarding:verified` dedup on `boardedAt`, `payment:succeeded` dedup on `paymentId`). **Ordering guarantees (§5.4)**: per-entity within one connection guaranteed; per-entity across reconnection not guaranteed; cross-entity not guaranteed. Client compares `ts` to drop out-of-order events.

**Authorization (§6)** per topic: `seat:availability:*` is public (any user with a valid schedule ID); `trip:live:*` requires booking OR SUPER_ADMIN; `booking:*` requires ownership OR SUPER_ADMIN; `admin:notifications` requires SUPER_ADMIN. Failed subscription closes connection with code 1008. **Rate-limited reconnection** (§6.6) blocks >10 reconnect attempts in 60s to prevent connection storms. **Size/rate limits** (§6.5) reference `09` §12.5.3's 64KB message size, 60/min per session, 5 max connections per user.

**Reconnection (§7)** has a state machine + backoff schedule — 1s, 2s, 4s, 8s, 16s across 5 retries, then polling. **Re-authentication** (§7.3) uses the `auth:expiring` → `auth:refresh` → `auth:refreshed` handshake 60s before JWT expiry with a 30s response window. **State recovery** (§7.4) requires refetching state after reconnect — never rely on missed events alone.

**Polling fallbacks (§8)** have canonical intervals — 3s for `seat:availability:*` and `trip:live:*`, 5s for `booking:*`, N/A for `admin:notifications` (no Phase 1 client). This resolves the G3 gap where `busverse/02` §15.1 and `busverse/04` §11.4 differed. **Fallback lifecycle** (§8.3): starts only after 5 WS reconnect failures, retries WS every 60s in parallel with polling, stops on WS reconnect. **UX** (§8.4) has 4 states — no indicator when connected, small "Reconnecting…" pill during retries, amber "Live updates paused — polling" during fallback, toast "Live updates restored" on recovery.

**Failure modes (§11)** cover 8 scenarios with defined behavior. **Graceful degradation (§11.4)** is 3-tier: WS → polling → manual refresh. **Never stuck:** the user can always manually refresh, with clear status indicators per §8.4.

**23 test vectors (§12)**: 16 payload validations (each canonical event's schema), 4 authorization tests (non-booked user rejected from `trip:live`, non-owner from `booking:*`, non-admin from `admin:notifications`, anonymous allowed on `seat:availability:*`), 3 reconnection tests (backoff → polling transition, fast reconnect, auth refresh during WS). `pnpm test:ws-catalog` runs in CI on every PR touching WS code. **Metrics (§13)** track `ws_connection_total`, `ws_active_connections`, `ws_events_emitted_total`, `ws_events_delivered_total`, `ws_events_failed_total`, `ws_publish_duration_ms`, `ws_reconnection_total`, `ws_auth_expiring_sent_total`, `ws_auth_refresh_total` with 5 alerts (high publish latency > 100ms → SEV2, high delivery failure > 1% → SEV2, high reconnection > 100/5min → SEV3, active connections > 500 → SEV3, auth failures > 10/5min → SEV2).

**Eight cross-doc amendments (§15)** — all non-breaking, no High-priority. A1 (Medium, Wave 2) adds `_v: 1`, `lockedByMe`, and `gps_anomaly` to `07` v1.3 §8.7. A2 (Medium, Wave 2) clarifies the GPS throttle in `07` v1.3 §8.7. A3 (Low, Wave 3) clarifies `admin:notifications` Phase 1 in `07` v1.3 §8.1. A4-A8 (Low, Wave 3) add reference updates to `busverse/02`, `busverse/04`, `buscon/05`, `buscon/04`, and `09`. **Unlike SH-03 which had 5 High-priority bug fixes, SH-04 is pure consolidation + versioning — no critical fixes.**

**Fifteen open questions** all confirmed by defaults — no blockers.

**The contract's central contribution is making the event stream verifiable.** Before SH-04, 16 events were scattered across 8 docs with partial schemas, contradictory throttle rates, and no versioning. After SH-04, there is one canonical catalog: 4 topics, 16 events, every field specified, every subscriber authorized per topic, every failure mode defined, every test vector enumerated. **The second contribution is resolving 3 material contradictions** — the GPS throttle (3s floor vs 5s cadence), the `admin:notifications` Phase 1 subscriber (none vs implied), and event versioning (unspecified vs `_v: 1`). **The third contribution is formalizing what was implicit** — `gps_anomaly` becomes a real event, `lockedByMe` becomes required, polling intervals become canonical, backoff schedule becomes documented. **Any future event addition or change goes through SH-04 — no product doc can add an event, modify a payload, or change a subscription rule without amending this catalog.**

### 2.3 Connection pool

| Parameter | Value | Why |
|---|---|---|
| Pool mode | Transaction | Fast release of connections |
| Max connections to Postgres | 100 | Safe for a single mid-size instance |
| App connection limit | 20 per API instance | Prevents one instance from starving others |
| Statement timeout | 30 s | Fails runaway queries |
| Idle-in-transaction timeout | 60 s | Catches leaked transactions |

## 3. Cross-Cutting Patterns

Every table follows these patterns. Defining them once means each schema section doesn't repeat them.

### 3.1 Standard column set

**Diagram: Standard columns on every table**
*Every table has a core set of columns for identity, auditing, soft delete, optimistic locking, and test isolation. Only `reference tables` (cities, stands) omit the `is_test` column because their data is real, not test.*

```mermaid
flowchart TB
    STD["Standard columns on every table"]

    STD --> PK["id uuid PK<br/>gen_random_uuid()"]
    STD --> AUD["created_at timestamptz<br/>updated_at timestamptz"]
    STD --> SD["deleted_at timestamptz<br/>nullable"]
    STD --> VL["version int default 0"]
    STD --> IT["is_test boolean<br/>transactional tables only"]

    IT --> T1["users, operators,<br/>bookings, payments,<br/>trips, audit_logs"]
    IT --> T2["❌ cities, stands<br/>(real geographic data)"]
```

**`is_test` propagation rule:**

| Table type | Has `is_test`? |
|---|---|
| Reference (cities, stands) | ❌ — real geographic data |
| Transactional (users, operators, bookings, payments, trips, sessions, audit_logs, consent_records, password_reset_tokens) | ✅ |
| Lookup (seat_layouts, seats, routes, route_stands, schedules) | ✅ — associated with test operators |

### 3.2 Trigger catalog

**Diagram: Trigger execution flow**
*Every mutable table has a trigger that fires on `UPDATE`. The trigger sets `updated_at = now()` and increments `version = version + 1`. Application code does not need to set either. If the application explicitly sets `version = ?` (optimistic lock check), the trigger still increments it.*

```mermaid
flowchart TD
    UPD["UPDATE statement"]
    UPD --> T["Trigger fires<br/>BEFORE UPDATE"]
    T --> SET["Set updated_at = now()<br/>Set version = version + 1"]
    SET --> CHK["Row written"]

    UPD -.->|"if version in WHERE clause"| CHK2["Optimistic lock check<br/>UPDATE ... WHERE version = ?"]
    CHK2 --> T
```

```sql
CREATE OR REPLACE FUNCTION trigger_set_updated()
RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at = now();
  NEW.version = OLD.version + 1;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```

**Applied to:** every mutable table via `CREATE TRIGGER set_updated BEFORE UPDATE ON {table} FOR EACH ROW EXECUTE FUNCTION trigger_set_updated();`

**Not applied to:** `audit_logs`, `gateway_webhooks`, `gps_samples`, `boarding_scans` — these are append-only and never updated.

### 3.3 Soft-delete query pattern

**Diagram: Soft-delete enforcement**
*Two enforcement layers — Prisma middleware auto-filters `WHERE deleted_at IS NULL` on every query; partial unique indexes ensure uniqueness works even with soft-deleted rows (e.g., a soft-deleted user's phone can be reused for a new registration).*

```mermaid
flowchart TB
    Q["Query"] --> MW["Prisma middleware<br/>auto-adds WHERE deleted_at IS NULL"]
    MW --> DB["Postgres executes"]

    DB --> PART["Partial unique index<br/>UNIQUE (phone) WHERE deleted_at IS NULL"]

    MW -.->|"override via skipFilter"| RAW["Raw query"]
    RAW --> DB
```

**Rules:**

- Every non-system query filters `WHERE deleted_at IS NULL` — enforced by Prisma middleware, not by hand
- Unique constraints are **partial**: `UNIQUE (phone) WHERE deleted_at IS NULL`, so a soft-deleted user's phone becomes available again
- System queries (audit, admin, analytics) may explicitly bypass the filter

### 3.4 Idempotency

**Rule:** Every money-path write carries an `idempotency_key`. Global unique, 24-hour window.

```sql
-- Partial unique index, so old keys can be pruned
CREATE UNIQUE INDEX uniq_payments_idempotency_key
  ON payments (idempotency_key)
  WHERE created_at > now() - interval '24 hours';
```

**Why global unique:** UUIDv4 idempotency keys are astronomically collision-resistant. Global unique allows retries from any client to be deduped. Pruning via partial index keeps the index small.

**Retry rule (per `07` §4.6):** A retry attempt after a FAILED payment MUST use a **new** `Idempotency-Key`. Reusing the same key returns the cached failed response — the user cannot retry. Same `bookingId`, new UUID for the key.

### 3.5 Multi-table transactions

Some operations span multiple tables and must be atomic. These are documented here so `08-WORKFLOWS.md` doesn't re-derive them.

| Operation | Tables touched | Atomicity |
|---|---|---|
| **Booking creation** | `bookings` (INSERT status=PENDING), `booking_passengers` (INSERT N rows), `seat_locks` (UPDATE expires_at = now() + 15 min — extend TTL for payment window) | ✅ One transaction |
| **Payment success (webhook)** | `payments` (UPDATE status=SUCCEEDED), `bookings` (UPDATE status=CONFIRMED), `tickets` (INSERT Ed25519-signed), `gst_invoices` (INSERT with sequential invoice_number), `gateway_webhooks` (INSERT with payload_hash), `seat_locks` (DELETE), `audit_logs` (INSERT async after commit) | ✅ One transaction |
| **Payment failure (webhook)** | `payments` (UPDATE status=FAILED), `bookings` (UPDATE status=FAILED), `gateway_webhooks` (INSERT with payload_hash), `seat_locks` (DELETE) | ✅ One transaction |
| **Payment timeout (cron)** | `payments` (UPDATE status=EXPIRED), `bookings` (UPDATE status=EXPIRED), `seat_locks` (DELETE), `audit_logs` (INSERT) | ✅ One transaction per booking |
| **Trip start** | `trips` (INSERT), `driver_profiles` (UPDATE on_duty=true), `sessions` (UPDATE metadata) | ✅ One transaction |
| **Trip end** | `trips` (UPDATE), `driver_profiles` (UPDATE on_duty=false) | ✅ One transaction |
| **Seat lock acquisition** | `seat_locks` (INSERT); Redis `SET NX` before DB; service-layer pre-check queries `booking_passengers` first | ⚠️ Redis is authority; DB is backup; pre-check prevents lock-on-booked |
| **Refund initiation** | `refunds` (INSERT with refund_tier), `payments` (UPDATE status) | ✅ One transaction |
| **Password reset consumption** | `password_reset_tokens` (UPDATE used_at), `operator_users`/`admin_users` (UPDATE password_hash), `sessions` (UPDATE revoked) | ✅ One transaction |
| **Consent grant** | `consent_records` (INSERT or UPDATE revoke existing) | ✅ One transaction |

**Rule:** The application opens one Postgres transaction per row above. Prisma's `$transaction()` with `isolationLevel: Serializable` where multi-row consistency is critical.

**Booking creation vs webhook transaction sequence (v1.2):**

1. **Client POST /bookings** — one transaction: `INSERT bookings (PENDING)`, `INSERT booking_passengers (N rows)`, `UPDATE seat_locks SET expires_at = now() + interval '15 minutes'` for each locked seat. **No ticket is created. No lock is deleted.** The lock protects the seat during the payment window.
2. **Client POST /payments** — one transaction: `INSERT payments (INITIATED)`. Razorpay order created outside the transaction, then the row updated with `gateway_order_id`.
3. **Razorpay webhook `payment.captured`** — one transaction: `INSERT gateway_webhooks`, `UPDATE payments SUCCEEDED`, `INSERT tickets` (Ed25519-signed QR, **first time this row exists**), `INSERT gst_invoices` (with sequential invoice_number), `UPDATE bookings CONFIRMED`, `DELETE seat_locks` (release the seat permanently). Audit row written async after commit.
4. **Razorpay webhook `payment.failed`** — one transaction: `INSERT gateway_webhooks`, `UPDATE payments FAILED`, `UPDATE bookings FAILED`, `DELETE seat_locks`. Passenger can retry with a new Idempotency-Key.
5. **`expire_pending_bookings` cron (15 min)** — one transaction per booking: `UPDATE payments EXPIRED`, `UPDATE bookings EXPIRED`, `DELETE seat_locks`, `INSERT audit_logs`.

**Why the ticket is INSERTed at webhook time (not at booking creation):** Invariant `05` §7.1 #1 requires "Every CONFIRMED booking has exactly one Ticket. PENDING/EXPIRED/FAILED bookings have no ticket." If a ticket were created at booking creation (PENDING state), it would exist before payment — violating the intent. The webhook transaction is the authoritative moment of confirmation, so the ticket is INSERTed there atomically with the status flip.

**Webhook DB error fallback (per `09` §13.5):** If the webhook transaction fails (DB down, constraint violation, timeout), the handler **first** writes the raw webhook body to `/tmp/webhooks/{uuid}.json`, **then** returns `200 OK` to Razorpay. A background replay job (`replay-local-webhooks`, runs every 60s) reads files from `/tmp/webhooks/` and retries the DB write. On success → delete file. On 10 consecutive failures → move to `/tmp/webhooks/failed/` + SEV1 alert. **No webhook is ever lost**, even if the DB is momentarily unavailable.


### 3.7 Invoice number generation

**Decision:** Financial-year-scoped Postgres SEQUENCE (April–March).

```sql
CREATE SEQUENCE invoice_number_seq_2026_27 START 1;
-- Application: SELECT nextval('invoice_number_seq_2026_27')
-- Format: INV/2026-27/00001
```

A cron creates next FY's sequence on March 1.

**Invoice creation timing (v1.2):** A `gst_invoices` row is INSERTed **only in the webhook `payment.captured` transaction** — the same transaction that confirms the booking and issues the ticket. No invoice exists for PENDING, EXPIRED, or FAILED bookings. The `invoice_number` is drawn from the sequence at that moment. After issuance, the invoice is immutable (no UPDATE trigger applied — see §7.4).

### 3.8 Hashing algorithms

| Hash target | Algorithm | Parameters |
|---|---|---|
| Password (`operator_users.password_hash`, `admin_users.password_hash`) | **Argon2id** | memory=64MB, iterations=3, parallelism=4 |
| OTP (`otp_challenges.otp_hash`) | **SHA-256** + salt | 16-byte random salt, stored alongside |
| Refresh token (`sessions.refresh_hash`) | **SHA-256** | Direct (no salt needed — token is high-entropy) |
| Password reset token (`password_reset_tokens.token_hash`) | **SHA-256** | Direct (token is high-entropy) |
| Phone for search (`users.phone_hash`) | **SHA-256** + fixed salt | Fixed salt in `.env` (deterministic for lookup) |
| **Webhook payload (`gateway_webhooks.payload_hash`)** | **SHA-256** | Direct (canonical JSON body, no salt — same body must produce same hash for dedup) |

**Why different algorithms:** Password hashing needs to be slow (defeats brute force). OTP, refresh tokens, reset tokens, and webhook payload hashes are already high-entropy or content-addressed — speed is fine. Phone hash must be deterministic (for lookup), so a fixed salt is used. Webhook payload hash must also be deterministic — if two identical webhook bodies arrive, the hash must match exactly.

### 4.2 `users`

**Purpose:** Identity anchor. One row per human. Contains the phone/email used for authentication. All profile tables reference `users.id`.

```sql
CREATE TABLE users (
  id             uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  phone          varchar(20) NOT NULL,
  phone_hash     varchar(64) NOT NULL,               -- SHA-256 of phone with fixed salt
  email          varchar(255),                        -- nullable
  email_verified boolean NOT NULL DEFAULT false,     -- verified flag (required for operator login)
  name           varchar(100),
  is_test        boolean NOT NULL DEFAULT false,
  created_at     timestamptz NOT NULL DEFAULT now(),
  updated_at     timestamptz NOT NULL DEFAULT now(),
  deleted_at     timestamptz,
  version        int NOT NULL DEFAULT 0,

  CONSTRAINT chk_users_phone_e164
    CHECK (phone ~ '^\+\d{10,15}$'),
  CONSTRAINT chk_users_email_lowercase
    CHECK (email IS NULL OR email = lower(email))
);

CREATE UNIQUE INDEX uniq_users_phone_active
  ON users (phone) WHERE deleted_at IS NULL;

CREATE UNIQUE INDEX uniq_users_phone_hash_active
  ON users (phone_hash) WHERE deleted_at IS NULL;

CREATE UNIQUE INDEX uniq_users_email_active
  ON users (email) WHERE deleted_at IS NULL AND email IS NOT NULL;

CREATE TRIGGER trg_users_updated
  BEFORE UPDATE ON users
  FOR EACH ROW EXECUTE FUNCTION trigger_set_updated();
```

**Column notes:**

- `phone` — E.164 format enforced by CHECK. Used for display and OTP.
- `phone_hash` — deterministic SHA-256 of phone, used for search without decrypting
- `email` — lowercased on insert; nullable because drivers may not have email
- `email_verified` — enforced for operator login (`04` §7.2). Passengers and drivers use OTP login only, so the flag is unused for them.
- `name` — cached from profile for quick display in admin lists

**`purpose` column (P2 security fix, Phase 2 — v1.3):** A challenge created with `purpose = 'LOGIN'` can only be consumed by `/verify` endpoints. A challenge created with `purpose = 'RESET'` can only be consumed by `/reset/verify`. Without this column, a LOGIN OTP could be submitted to `/reset/verify` and change the user's password — a full account takeover. The Phase 2 migration `20261027190000_add_otp_purpose` added this column and the compound index. `consumeOtpChallenge()` filters by purpose; `createOtpChallenge()` writes it.

**Migration note:** The `purpose` column was added in Phase 2 with `DEFAULT 'LOGIN'` to backfill existing rows. Existing challenges from before the migration are treated as LOGIN challenges, which is correct — they were all issued for login.

```sql
  purpose        varchar(50) NOT NULL CHECK (purpose IN (
                   'terms_of_service','privacy_policy','marketing','analytics')),
  policy_version varchar(20) NOT NULL,                  -- e.g. 'v1.0'
  granted_at     timestamptz NOT NULL DEFAULT now(),
  revoked_at     timestamptz,                           -- soft-revoke; row preserved for audit
  ip_address     inet,                                  -- source of consent (DPDP §7(1))
  created_at     timestamptz NOT NULL DEFAULT now(),
  updated_at     timestamptz NOT NULL DEFAULT now(),
  deleted_at     timestamptz,
  version        int NOT NULL DEFAULT 0,
  is_test        boolean NOT NULL DEFAULT false
);

CREATE INDEX idx_consent_records_user_id
  ON consent_records (user_id) WHERE deleted_at IS NULL;

-- Only one ACTIVE consent per (user, purpose). Revoke (set revoked_at) to create a new one.
CREATE UNIQUE INDEX uniq_consent_records_user_purpose_active
  ON consent_records (user_id, purpose)
  WHERE revoked_at IS NULL AND deleted_at IS NULL;

CREATE TRIGGER trg_consent_records_updated
  BEFORE UPDATE ON consent_records
  FOR EACH ROW EXECUTE FUNCTION trigger_set_updated();
```

**Rules:**

- Consent is granted per `(user_id, purpose)`. To re-consent after revoking, a new row is created with a new `policy_version`.
- The `ip_address` is captured for DPDP §7(1) audit requirements.
- `version` int is the standard optimistic-lock column; `policy_version` varchar is the policy string (e.g. "v1.0").
- Rows are never hard-deleted — DPDP requires consent history. `deleted_at` is only set when the owning user is deleted (via CASCADE).

### 4.11 `password_reset_tokens`

**Purpose:** Stores one-time password reset tokens (SHA-256 hashed) with expiry. Referenced by `04` §7.6 and `07` §3.7.

```sql
CREATE TABLE password_reset_tokens (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id     uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  token_hash  varchar(64) NOT NULL UNIQUE,             -- SHA-256 of the raw token sent by email
  expires_at  timestamptz NOT NULL,                    -- 30 min from issuance
  used_at     timestamptz,                             -- set when consumed; prevents reuse
  ip_address  inet,
  created_at  timestamptz NOT NULL DEFAULT now(),
  updated_at  timestamptz NOT NULL DEFAULT now(),
  deleted_at  timestamptz,
  version     int NOT NULL DEFAULT 0,
  is_test     boolean NOT NULL DEFAULT false
);

CREATE INDEX idx_password_reset_tokens_user_id
  ON password_reset_tokens (user_id) WHERE deleted_at IS NULL;

CREATE INDEX idx_password_reset_tokens_expires
  ON password_reset_tokens (expires_at) WHERE used_at IS NULL;

CREATE TRIGGER trg_password_reset_tokens_updated
  BEFORE UPDATE ON password_reset_tokens
  FOR EACH ROW EXECUTE FUNCTION trigger_set_updated();
```

**Rules:**

- The raw token is generated server-side (32 random bytes, base64) and sent via email; only the SHA-256 hash is stored.
- Consuming a token sets `used_at` (via transaction). A second consumption attempt returns `401 RESET_TOKEN_INVALID`.
- Multiple active tokens per user are allowed (user can request a second email if the first is lost).
- Purged nightly by retention job (`purge_password_reset_tokens`, §15).

## 6. Booking Schema

**The Booking context holds 4 tables.** `seat_locks` and `bookings` are separate roots. `bookings` owns `booking_passengers` and `tickets`.

### 6.1 Booking ERD

**Diagram: Booking context ERD**
*Four Booking tables. `seat_locks` is ephemeral, deleted on TTL or on payment success. `bookings` is the immutable purchase. `booking_passengers` and `tickets` are children of `bookings`. The unique constraint on `(schedule_id, seat_id)` in both `seat_locks` and `booking_passengers` is the DB-level guarantee of no double-locking and no double-booking.*

**Lock TTL lifecycle (v1.2):**

| Phase | TTL | Set by |
|---|---|---|
| Lock acquired via POST /seat-locks | 5 minutes | Application |
| Booking created (POST /bookings) | Extended to 15 minutes | `UPDATE seat_locks SET expires_at = now() + interval '15 minutes'` in booking transaction |
| Payment success (webhook) | Lock deleted | Webhook transaction `DELETE seat_locks` |
| Payment failure (webhook) | Lock deleted | Webhook transaction `DELETE seat_locks` |
| Payment timeout (cron) | Lock deleted | `expire_pending_bookings` cron |

**Note on service-layer pre-check (invariant #8):** Before acquiring a lock in POST /seat-locks, the service queries `booking_passengers` for the same `(schedule_id, seat_id)`. If a row exists, returns `409 SEAT_ALREADY_BOOKED` without attempting the lock. This prevents a malicious client from bypassing the UI and locking an already-booked seat. There is no cross-table unique constraint (would require a trigger); the service-layer guard is sufficient for Phase 1 volume.

**Invoice generation timing (v1.2, per `05` §6.4 and §3.7):** A `gst_invoices` row is INSERTed **in the same transaction as the webhook `payment.captured` handler** — the transaction that UPDATEs `payments SUCCEEDED`, UPDATEs `bookings CONFIRMED`, and INSERTs `tickets`. ### 7.5 `gateway_webhooks`

```sql
CREATE TABLE gateway_webhooks (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  payment_id   uuid NOT NULL REFERENCES payments(id) ON DELETE CASCADE,
  event_type   varchar(50) NOT NULL CHECK (event_type IN (
                 'payment.captured','payment.failed',
                 'refund.processed','refund.failed')),
  payload_hash varchar(64) NOT NULL,                 -- SHA-256 of raw webhook body, computed by app
  payload_json jsonb NOT NULL,
  signature    varchar(200) NOT NULL,
  received_at  timestamptz NOT NULL DEFAULT now(),
  is_test      boolean NOT NULL DEFAULT false
);

CREATE INDEX idx_gateway_webhooks_payment_id ON gateway_webhooks (payment_id);
CREATE INDEX idx_gateway_webhooks_received_at ON gateway_webhooks (received_at);

-- THE critical constraint: replay protection.
-- Duplicate (payment_id, event_type, payload_hash) rows are rejected at DB level.
-- The app catches this unique violation and returns 200 no-op to Razorpay (per 09 §13.4).
CREATE UNIQUE INDEX uniq_gateway_webhooks_dedup
  ON gateway_webhooks (payment_id, event_type, payload_hash);

-- No UPDATE trigger — append-only. No deleted_at — purged by retention job at 90 days (§15).
```

**`payload_hash` computation:**

```
payload_hash = sha256(raw_request_body).hex()   // raw body, before JSON parsing
```

Computed by the webhook handler before the transaction opens. If a payload hash collision is astronomically unlikely but possible, the app treats the second row as a duplicate and returns 200. The unique constraint is what makes this guarantee real.

**Note:** This constraint is the backing for `09` §13.4's claim that "Payload hash uniqueness | `gateway_webhooks` unique on `(payment_id, event_type, payload_hash)`". Without it, webhook replay protection would be a paper claim.

### 8.3 `gps_samples` (partitioned daily)

```sql
CREATE TABLE gps_samples (
  id                          uuid NOT NULL DEFAULT gen_random_uuid(),
  trip_id                     uuid NOT NULL,                     -- soft FK to trips
  lat                         numeric(9,6) NOT NULL,
  lng                         numeric(9,6) NOT NULL,
  speed_kmh                   numeric(5,2),                      -- computed by server
  accuracy_m                  numeric(5,2),                      -- v1.3 (A4): client-reported accuracy
  client_reported_speed_kmh   numeric(5,2),                      -- v1.3 (A4): client-reported (provenance)
  received_at                 timestamptz NOT NULL DEFAULT now(), -- v1.3 (A2): server-side receive time
  recorded_at                 timestamptz NOT NULL,              -- client clock
  PRIMARY KEY (id, recorded_at)
) PARTITION BY RANGE (recorded_at);

-- Application creates tomorrow's partition via cron
CREATE TABLE gps_samples_2026_10_24 PARTITION OF gps_samples
  FOR VALUES FROM ('2026-10-24 00:00:00+00') TO ('2026-10-25 00:00:00+00');

CREATE INDEX idx_gps_samples_trip_recorded
  ON gps_samples (trip_id, recorded_at DESC);
```

**`received_at` (A2 — applied Phase 1a):** Server-side timestamp when the GPS sample hit the API. Distinct from `recorded_at` (client's own clock at sample time). The 6-check provenance pipeline in Phase 6 compares `received_at` vs `recorded_at` to detect forged timestamps, clock drift, and replay.

**`accuracy_m` (A4 — applied Phase 1a):** Client-reported GPS accuracy in meters (from `navigator.geolocation` or Expo's `Location.Accuracy`). Used by ETA computation to weight samples — a 5m accuracy sample is trusted more than a 100m accuracy sample for the same lat/lng. Nullable — some devices don't report accuracy.

**`client_reported_speed_kmh` (A4 — applied Phase 1a):** What the client said its speed was. Kept distinct from `speed_kmh` (which the server computes by comparing consecutive samples' lat/lng/time). Mismatch between these two is one of the 6 provenance signals that raises `gps_anomaly` in Phase 6.

**Note:** No FK to `trips` — partitioned tables can't participate in FKs efficiently. Application guarantees `trip_id` refers to an existing trip. `gps_samples` is append-only, no `updated_at`, `version`, or `deleted_at`.

## 10. Constraint Catalog and Error Codes

### 10.1 Constraint → Error code mapping

**Diagram: Constraint enforcement hierarchy**
*Write requests pass through four layers: app validation, DB CHECK, DB UNIQUE, DB FK. Each layer maps to a specific HTTP status and error code. The API translates Prisma's P2002/P2003/P2004 errors into domain-specific codes. Webhook dedup is a special case — the app catches the unique violation and returns 200 no-op, not an error.*

```mermaid
flowchart TD
    REQ["INSERT / UPDATE"]
    REQ --> APP["App validation"]
    APP --> CHK["DB CHECK"]
    CHK --> UK["DB UNIQUE"]
    UK --> FK["DB FK"]
    FK --> OK["COMMIT"]

    APP -->|"fail"| E400["400 DOMAIN_ERROR"]
    CHK -->|"fail"| E400
    UK -->|"fail"| E409["409 CONFLICT_CODE"]
    UK -.->|"webhook dedup"| NOOP["200 no-op<br/>(app catches)"]
    FK -->|"fail"| E400["400 REFERENTIAL_ERROR"]
```

**Webhook dedup note:** `uniq_gateway_webhooks_dedup` is a unique constraint, but it never surfaces as an error to the client. The webhook handler:
1. Computes `payload_hash = sha256(raw_body).hex()`
2. Begins transaction
3. Inserts `gateway_webhooks` row
4. If insert raises `23505` (unique_violation) on `uniq_gateway_webhooks_dedup` → rollback, return `200 OK` (no-op). Per `09` §13.4, this is the replay-prevention path.
5. If insert succeeds → process payment status change → commit → return `200 OK`

The constraint is not in the API error catalog — it is a security control enforced silently.

## 11. Index Strategy

**Diagram: Index categories and hot paths**
*Four index categories: primary keys (automatic), foreign key indexes (for join performance), unique constraint indexes (for invariants), and query-optimization indexes (for hot paths). The hot-path list on the right covers the top-8 access patterns from `01-PLAN-AND-SCOPE.md` demo criteria, plus the new payment-timeout index.*

```mermaid
flowchart TB
    IDX["All indexes"]

    IDX --> PK["Primary keys<br/>automatic"]
    IDX --> FK["FK indexes<br/>1 per FK"]
    IDX --> UK["Unique constraints"]
    IDX --> HP["Hot paths"]

    HP --> H1["login: users.phone_hash"]
    HP --> H2["refresh: sessions.refresh_hash"]
    HP --> H3["my-trips: bookings.(user_id, status)"]
    HP --> H4["search: schedules.(route_id, departure_time)"]
    HP --> H5["lock cleanup: seat_locks.expires_at"]
    HP --> H6["driver trip: trips.(driver_id, status)"]
    HP --> H7["manifest: boarding_scans.trip_id"]
    HP --> H8["audit: audit_logs.(entity_type, entity_id)"]
    HP --> H9["payment timeout: bookings.(created_at) WHERE status=PENDING"]
```

**Index policy:**

- Every FK has an index (non-negotiable, avoids full scans on cascade)
- Every unique constraint is backed by an index
- Hot-path queries get composite indexes
- No speculative indexes — measure first
- Partial indexes for filtered queries (`WHERE deleted_at IS NULL`)
- No index on low-cardinality booleans (`is_test` alone is never indexed)

**Performance targets:**

| Query | p95 target |
|---|---|
| Login (phone lookup) | < 50 ms |
| Refresh token validation | < 20 ms |
| Search schedules | < 200 ms |
| Seat lock acquisition | < 50 ms |

## 15. Retention Jobs

**Diagram: Retention job schedule**
*Nightly cron at 02:00 UTC runs **nine** retention jobs. Each job is idempotent. GPS retention uses `DROP PARTITION` (O(1)); other jobs use `DELETE ... WHERE` (indexed). The new `expire_pending_bookings` job (v1.2) handles the 15-minute payment timeout — releasing seats and marking PENDING bookings EXPIRED. Failures alert but do not break subsequent jobs.*

```mermaid
flowchart LR
    CRON["Nightly 02:00 UTC"]

    CRON --> J1["purge_gps_partitions<br/>DROP > 90 days"]
    CRON --> J2["purge_sessions<br/>DELETE > 180 days"]
    CRON --> J3["purge_otp_challenges<br/>DELETE > 1 hour expired"]
    CRON --> J4["purge_gateway_webhooks<br/>DELETE > 90 days"]
    CRON --> J5["purge_seat_locks<br/>DELETE expired"]
    CRON --> J6["purge_idempotency_keys<br/>UPDATE to allow reuse"]
    CRON --> J7["reset_stale_on_duty<br/>trips + drivers > 6h"]
    CRON --> J8["purge_password_reset_tokens<br/>DELETE expired or used"]
    CRON --> J9["expire_pending_bookings<br/>PENDING > 15 min → EXPIRED"]
```

| Job | Table | Condition | Method |
|---|---|---|---|
| `purge_gps_partitions` | `gps_samples` | Partition older than 90 days | `DROP TABLE partition` |
| `purge_sessions` | `sessions` | `created_at < now() - 180d` | `DELETE` |
| `purge_otp_challenges` | `otp_challenges` | `expires_at < now() - 1h` | `DELETE` |
| `purge_gateway_webhooks` | `gateway_webhooks` | `received_at < now() - 90d` | `DELETE` |
| `purge_seat_locks` | `seat_locks` | `expires_at < now()` | `DELETE` |
| `purge_idempotency_keys` | `payments` | `created_at < now() - 24h` | `DELETE` (frees idempotency index) |
| `reset_stale_on_duty` | `driver_profiles` | `on_duty = true` + no active trip + updated > 6h | `UPDATE on_duty = false` |
| `purge_password_reset_tokens` | `password_reset_tokens` | `expires_at < now() - 1h` OR `used_at IS NOT NULL AND created_at < now() - 24h` | `DELETE` |
| **`expire_pending_bookings`** | **`bookings` + `payments` + `seat_locks`** | **`bookings.status = 'PENDING'` AND `bookings.created_at < now() - interval '15 minutes'`** | **Per-booking transaction: `UPDATE payments EXPIRED`; `UPDATE bookings EXPIRED`; `DELETE seat_locks`; `INSERT audit_logs action='booking_expired'`** |

**`expire_pending_bookings` — full specification (v1.2):**

```sql
-- Runs every 5 minutes (not just nightly) to bound the delay for a user who refreshes the page
-- after the 15-min window. Nightly batch is a safety net.

WITH expired AS (
  SELECT b.id AS booking_id, b.schedule_id, b.user_id
  FROM bookings b
  WHERE b.status = 'PENDING'
    AND b.created_at < now() - interval '15 minutes'
    AND b.deleted_at IS NULL
  LIMIT 100  -- batch to avoid long locks
)
SELECT b.booking_id, b.schedule_id, b.user_id, bp.seat_id
FROM expired b
JOIN booking_passengers bp ON bp.booking_id = b.booking_id;

-- For each row in the batch, in one transaction:
BEGIN;
  UPDATE payments SET status = 'EXPIRED', expired_at = now()
    WHERE booking_id = :booking_id AND status IN ('INITIATED','PENDING');
  UPDATE bookings SET status = 'EXPIRED', expired_at = now()
    WHERE id = :booking_id AND status = 'PENDING';
  DELETE FROM seat_locks
    WHERE schedule_id = :schedule_id AND seat_id IN (:seat_ids);
  INSERT INTO audit_logs (entity_type, entity_id, action, occurred_at)
    VALUES ('Booking', :booking_id, 'booking_expired', now());
COMMIT;
```

**Retention note:** `expire_pending_bookings` runs **every 5 minutes** as a BullMQ job — not just the nightly cron — so that a user who refreshes after 15 min sees the correct EXPIRED state, and seats are released back to inventory quickly. The nightly entry in the table above is the safety-net sweep.

**Webhook retention note:** `purge_gateway_webhooks` deletes rows older than 90 days. This is well beyond the 5-minute timestamp check and 24-hour payment-status no-op window from `09` §13.4, so replaying an old webhook after purge would be treated as a new event — but it would fail the timestamp check first (5 min), so it would 401 before any state change. Safe.

## 16. Migrations

**Diagram: Migration lifecycle**
*Prisma migrations. Developer edits schema, generates migration, reviews SQL, tests locally, commits. Staging applies via `migrate deploy`; production after staging passes. Rollbacks are manual and documented. Zero-downtime rules apply to always-hot tables (users, bookings, payments).*

```mermaid
flowchart LR
    DEV["Edit schema<br/>prisma/schema.prisma"]
    DEV --> GEN["prisma migrate dev<br/>generates SQL"]
    GEN --> REV["Review generated SQL"]
    REV --> TEST["Test on local DB"]
    TEST --> COMMIT["Commit migration"]
    COMMIT --> STAGE["migrate deploy<br/>on staging"]
    STAGE --> PROD["migrate deploy<br/>on production"]
```

**Migration rules:**

| Rule | Detail |
|---|---|
| Tool | Prisma Migrate |
| Directory | `prisma/migrations/{timestamp}_{name}/migration.sql` |
| Naming | `YYYYMMDDHHMMSS_{verb}_{noun}` — e.g. `20261115120000_add_qr_payload` |
| Reversible | Every migration has a documented rollback in `prisma/migrations/ROLLBACKS.md` |
| Dry run | Every migration PR runs against staging first |
| Zero downtime | Required for `users`, `bookings`, `payments`, `sessions` — two-phase add-column or backfill-then-constrain |

**Zero-downtime rules:**

- Adding a column: nullable first, backfill, then set NOT NULL in a separate migration
- Adding an index: `CREATE INDEX CONCURRENTLY`
- Renaming a column: add new, dual-write, backfill, drop old (three migrations)
- Dropping a column: two-phase (mark deprecated, then drop after one release)

**Migration note for `payload_hash`:** The `payload_hash` column is `NOT NULL` with no default. Adding it to a live table with existing rows would fail. When this column is introduced (this migration), the sequence must be:
1. Add `payload_hash varchar(64)` (nullable)
2. Backfill: compute hash from `payload_json` for every existing row
3. Add `NOT NULL` constraint
4. Add `uniq_gateway_webhooks_dedup` index (`CREATE UNIQUE INDEX CONCURRENTLY`)
This is a multi-step zero-downtime migration for `gateway_webhooks` when it already has rows in staging/prod. In a fresh DB (dev, CI, initial staging), single migration is fine.

**Migration note for `refund_tier` (v1.2):** The `refund_tier` column is `NOT NULL`. Same pattern:
1. Add `refund_tier varchar(20)` (nullable)
2. Backfill: compute tier from `bookings.cancelled_at` vs `schedules.departure_time` for existing refunds
3. Add `NOT NULL` + `CHECK` constraint
4. Add to enum catalog and validation

**Migration note for `expired_at` (v1.2):** New columns `bookings.expired_at` and `payments.expired_at` are nullable — safe to add in a single migration.

**Migration note for `purpose` (v1.3 — Phase 2):** Applied as `20261027190000_add_otp_purpose`. Column added with `DEFAULT 'LOGIN'` to backfill existing rows; existing rows become LOGIN challenges which is correct. Compound index `idx_otp_challenges_phone_purpose_expires` added via `CREATE INDEX CONCURRENTLY`.

**Migration note for A2/A4/A6/DA3 (v1.3 — Phase 1a):** All applied as part of the `20261027092835_init` migration:
- `buses.bus_type` (5-enum) + `buses.amenities_json` (JSONB) — new columns, migration is single-step
- `gps_samples.accuracy_m`, `gps_samples.client_reported_speed_kmh`, `gps_samples.received_at` — new columns on partitioned table, added before partition creation in migration
- `trips.distance_km` — nullable, single-step
- `seats.seat_label` narrowed from `varchar(10)` to `varchar(4)` — was pre-populated fresh so no backfill needed

## 22. One-Paragraph Summary

**BusVerse + BusCon Phase 1 runs on PostgreSQL 16 with 31 tables across 6 bounded contexts, backed by pgcrypto for UUID generation and pg_trgm for future search. Every mutable table carries a standard column set — `id uuid` PK, `created_at`, `updated_at`, `deleted_at`, `version int`, and (for transactional tables only) `is_test boolean` — with `updated_at` and `version` maintained by a shared `trigger_set_updated()` function. Soft delete is enforced via Prisma middleware with partial unique indexes so soft-deleted rows do not block re-registration. Money is stored as `bigint` paise, enums as `varchar(50) + CHECK` constraints, JSONB columns with a `_v` version field, and phone numbers in E.164 with a deterministic SHA-256 `phone_hash` for search. **The DB-level guarantee of no double-locking is a unique constraint on `(schedule_id, seat_id)` in `seat_locks`; the guarantee of no double-booking is a unique constraint on `(schedule_id, seat_id)` in `booking_passengers`. In v1.2, the booking creation transaction no longer deletes the lock or creates a ticket — it INSERTs `bookings (PENDING)` + `booking_passengers` + extends the lock TTL to 15 min. The webhook `payment.captured` transaction atomically UPDATEs `payments SUCCEEDED`, UPDATEs `bookings CONFIRMED`, INSERTs `tickets` (Ed25519-signed), INSERTs `gst_invoices` (with sequential invoice_number), INSERTs `gateway_webhooks` (with payload_hash), and DELETEs `seat_locks`. This sequencing enforces invariants #1 (CONFIRMED bookings have exactly one ticket) and #18 (ticket cannot exist without payment) at the transaction level. A 9th retention job (`expire_pending_bookings`, running every 5 minutes) handles the 15-minute payment timeout — transitioning PENDING bookings to EXPIRED, `payments` to EXPIRED, and releasing the associated `seat_locks`.** Booking references and GST invoice numbers are generated via year-scoped and financial-year-scoped Postgres SEQUENCEs. Passwords use Argon2id on `operator_users.password_hash` and `admin_users.password_hash`, OTPs and refresh tokens and reset tokens and phone hashes and webhook payload hashes use SHA-256, and Restricted PII fields (phone, PAN, license, ID, card details) are encrypted at rest with AES-256-GCM plus searchable hash columns. **`gateway_webhooks` carries a `payload_hash varchar(64)` column populated by the app (SHA-256 of the raw webhook body) plus a `uniq_gateway_webhooks_dedup` unique index on `(payment_id, event_type, payload_hash)` — the DB-level backing for `09` v1.1 §13.4's replay-protection claim. Duplicates raise `23505` and the app catches it, returns `200 OK` no-op, and never enters the state-change transaction. On DB error during webhook processing, the handler writes the raw body to `/tmp/webhooks/{uuid}.json` before returning 200 (per `09` §13.5) — a background replay job retries the DB write. No webhook is ever lost.** `refunds` carries a new `refund_tier` column with 5 enum values (`TIER_FULL`, `TIER_75`, `TIER_50`, `TIER_ZERO`, `TIER_NOT_ELIGIBLE`) — the canonical refund calculation per `07` v1.2 §4.5. Two tables are partitioned — `audit_logs` monthly (retained forever) and `gps_samples` daily (retained 90 days, dropped via partition DROP). **Nine retention cron jobs run at 02:00 UTC plus a 5-min interval for `expire_pending_bookings`, including password-reset-token purge and gateway-webhook purge at 90 days.** The Identity context includes `consent_records` (DPDP §7(1) consent per user per purpose with policy version and IP capture, soft-revoke pattern) and `password_reset_tokens` (SHA-256 hashed one-time reset tokens with 30-min expiry, single-use via `used_at`), plus deferred `operator_id` FK constraints from `operator_users` and `driver_profiles` to `operators`. Migrations use Prisma Migrate with documented rollbacks and zero-downtime rules — including specific paths for `payload_hash`, `refund_tier`, `expired_at`, `purpose`, and the Phase 1a A2/A4/A6/DA3 columns. Seed scripts are idempotent UPSERTs producing **380 rows** (matching actual Phase 10 seed) across the Delhi → Kanpur → Lucknow demo corridor, including seed consent records for every user. A constraint-to-error-code catalog maps every DB violation to an API error code — except `uniq_gateway_webhooks_dedup`, which is deliberately silent (returns 200 no-op). **One hundred and thirty-three schema tests** enforce constraints, FKs, cascades, partitions, retention (including payment timeout), triggers, webhook dedup, refund_tier validation, otp_purpose isolation, and seed idempotency. Eleven open questions remain, all Phase-2-decidable defaults, none blocking.

import { ApiResponse, ApiError, ApiErrorResponse } from './types';
import { CONFIG } from '../config';

type HttpMethod = 'GET' | 'POST' | 'PUT' | 'PATCH' | 'DELETE';

interface RequestOptions {
  method?: HttpMethod;
  body?: unknown;
  headers?: Record<string, string>;
  idempotencyKey?: string;
  skipAuth?: boolean;
}

// Global refresh queue to avoid token refresh races across concurrent calls
let isRefreshing = false;
let refreshSubscribers: Array<(token: string) => void> = [];

function onTokenRefreshed(token: string) {
  refreshSubscribers.forEach((callback) => callback(token));
  refreshSubscribers = [];
}

function addRefreshSubscriber(callback: (token: string) => void) {
  refreshSubscribers.push(callback);
}

export class HttpClient {
  private baseUrl: string;

  constructor() {
    // In browser: use relative '/api/v1' to hit Next.js rewrite proxy (zero CORS drift)
    // Server-side: use absolute backend URL from config
    this.baseUrl = typeof window !== 'undefined' ? '/api/v1' : CONFIG.API_BASE;
  }

  private getAccessToken(): string | null {
    if (typeof window === 'undefined') return null;
    return localStorage.getItem('busverse_access_token');
  }

  private getRefreshToken(): string | null {
    if (typeof window === 'undefined') return null;
    return localStorage.getItem('busverse_refresh_token');
  }

  private setTokens(accessToken: string, refreshToken: string) {
    if (typeof window === 'undefined') return;
    localStorage.setItem('busverse_access_token', accessToken);
    localStorage.setItem('busverse_refresh_token', refreshToken);
  }

  private clearAuthAndLogout() {
    if (typeof window === 'undefined') return;
    localStorage.removeItem('busverse_access_token');
    localStorage.removeItem('busverse_refresh_token');
    localStorage.removeItem('busverse_user');
    window.dispatchEvent(new CustomEvent('busverse:auth:logout'));
  }

  public async request<T>(endpoint: string, options: RequestOptions = {}): Promise<ApiResponse<T>> {
    const { method = 'GET', body, headers = {}, idempotencyKey, skipAuth = false } = options;

    const targetUrl = endpoint.startsWith('http')
      ? endpoint
      : `${this.baseUrl}${endpoint.startsWith('/') ? endpoint : `/${endpoint}`}`;

    const requestHeaders: Record<string, string> = {
      'Content-Type': 'application/json',
      'X-Request-Id': `req_${crypto.randomUUID().slice(0, 12)}`,
      ...headers,
    };

    if (idempotencyKey) {
      requestHeaders['Idempotency-Key'] = idempotencyKey;
    }

    if (!skipAuth) {
      const token = this.getAccessToken();
      if (token) {
        requestHeaders['Authorization'] = `Bearer ${token}`;
      }
    }

    const config: RequestInit = {
      method,
      headers: requestHeaders,
    };

    if (body !== undefined && method !== 'GET') {
      config.body = JSON.stringify(body);
    }

    const response = await fetch(targetUrl, config);

    // 401 Unauthorized handling: Auto-rotate access token and replay
    if (response.status === 401 && !skipAuth) {
      const refreshToken = this.getRefreshToken();
      if (!refreshToken) {
        this.clearAuthAndLogout();
        const errJson = (await response.json().catch(() => ({}))) as ApiErrorResponse;
        throw new ApiError(401, errJson.error || { code: 'TOKEN_EXPIRED', message: 'Session expired' });
      }

      if (!isRefreshing) {
        isRefreshing = true;

        this.performTokenRefresh(refreshToken)
          .then((newAccessToken) => {
            isRefreshing = false;
            onTokenRefreshed(newAccessToken);
          })
          .catch((refreshErr) => {
            isRefreshing = false;
            refreshSubscribers = [];
            this.clearAuthAndLogout();
            throw refreshErr;
          });
      }

      // Wait for active refresh to resolve, then replay original request
      return new Promise((resolve, reject) => {
        addRefreshSubscriber(async (newAccessToken: string) => {
          try {
            requestHeaders['Authorization'] = `Bearer ${newAccessToken}`;
            const replayed = await fetch(targetUrl, { ...config, headers: requestHeaders });
            const data = await this.handleResponse<T>(replayed);
            resolve(data);
          } catch (replayErr) {
            reject(replayErr);
          }
        });
      });
    }

    // 403 Forbidden: NON-NEGOTIABLE RULE 8.3 â€” NEVER attempt refresh on 403 (role mismatch)
    return this.handleResponse<T>(response);
  }

  private async performTokenRefresh(refreshToken: string): Promise<string> {
    const refreshUrl = `${this.baseUrl}/passenger/auth/refresh`;
    const res = await fetch(refreshUrl, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ refreshToken }),
    });

    if (!res.ok) {
      this.clearAuthAndLogout();
      throw new ApiError(res.status, {
        code: 'SESSION_REVOKED',
        message: 'Your credentials could not be rotated. Please log in again.',
      });
    }

    const payload = (await res.json()) as ApiResponse<{
      accessToken: string;
      refreshToken: string;
    }>;

    this.setTokens(payload.data.accessToken, payload.data.refreshToken);
    return payload.data.accessToken;
  }

  private async handleResponse<T>(response: Response): Promise<ApiResponse<T>> {
    const contentType = response.headers.get('content-type');
    const isJson = contentType && contentType.includes('application/json');

    if (!response.ok) {
      if (isJson) {
        const errorJson = (await response.json()) as ApiErrorResponse;
        throw new ApiError(
          response.status,
          errorJson.error || {
            code: 'INTERNAL_ERROR',
            message: `Request failed with status ${response.status}`,
          }
        );
      }
      throw new ApiError(response.status, {
        code: 'NETWORK_ERROR',
        message: response.statusText || 'Network request failed',
      });
    }

    if (response.status === 204) {
      return { data: {} as T };
    }

    return (await response.json()) as ApiResponse<T>;
  }

  // Convenience verbs
  public get<T>(endpoint: string, headers?: Record<string, string>) {
    return this.request<T>(endpoint, { method: 'GET', headers });
  }

  public post<T>(endpoint: string, body?: unknown, options: Omit<RequestOptions, 'method' | 'body'> = {}) {
    return this.request<T>(endpoint, { method: 'POST', body, ...options });
  }

  public patch<T>(endpoint: string, body?: unknown, headers?: Record<string, string>) {
    return this.request<T>(endpoint, { method: 'PATCH', body, headers });
  }

  public delete<T>(endpoint: string, headers?: Record<string, string>) {
    return this.request<T>(endpoint, { method: 'DELETE', headers });
  }
}

export const api = new HttpClient();

import { io, Socket } from 'socket.io-client';
import { CONFIG } from '../config';

type SocketEventListener = (payload: any) => void;

class WebSocketManager {
  private socket: Socket | null = null;
  private subscribedTopics: Set<string> = new Set();
  private listeners: Map<string, Set<SocketEventListener>> = new Map();
  private authTimeoutTimer: NodeJS.Timeout | null = null;

  public connect(accessToken: string) {
    if (this.socket && this.socket.connected) {
      return;
    }

    if (this.socket) {
      this.socket.disconnect();
    }

    // Connect to backend Fastify Socket.io server
    this.socket = io(CONFIG.WS_URL, {
      path: '/v1/ws',
      transports: ['websocket', 'polling'],
      reconnectionDelay: 1000,
      reconnectionDelayMax: 16000,
      reconnectionAttempts: 5,
      autoConnect: true,
    });

    // RULE 8.11: Handshake timing â€” server terminates after 5s if auth is delayed
    this.socket.on('connect', () => {
      this.socket?.emit('message', {
        action: 'auth',
        token: accessToken,
      });

      // Clear safeguard timer once connect initiates
      if (this.authTimeoutTimer) clearTimeout(this.authTimeoutTimer);
    });

    this.socket.on('auth:ok', () => {
      // Re-subscribe to all active topics on reconnection
      if (this.subscribedTopics.size > 0) {
        this.socket?.emit('message', {
          action: 'subscribe',
          topics: Array.from(this.subscribedTopics),
        });
      }
    });

    // Server sends auth:expiring at (exp - 60s)
    this.socket.on('auth:expiring', async () => {
      const refreshToken = localStorage.getItem('busverse_refresh_token');
      if (refreshToken && this.socket) {
        this.socket.emit('message', {
          action: 'auth:refresh',
          refreshToken,
        });
      }
    });

    this.socket.on('auth:refreshed', (data: { accessToken: string; refreshToken: string }) => {
      localStorage.setItem('busverse_access_token', data.accessToken);
      localStorage.setItem('busverse_refresh_token', data.refreshToken);
    });

    // General message router for incoming events
    this.socket.on('message', (msg: { event?: string; topic?: string; data?: any }) => {
      if (msg.event) {
        const topicListeners = this.listeners.get(msg.event);
        if (topicListeners) {
          topicListeners.forEach((listener) => listener(msg.data));
        }
      }
    });

    // Close code management
    this.socket.on('disconnect', (reason) => {
      if (reason === 'io server disconnect') {
        // Closed by server (e.g., Code 4001, 4003 or 1008)
        const freshToken = localStorage.getItem('busverse_access_token');
        if (freshToken) {
          setTimeout(() => this.connect(freshToken), 1500);
        }
      }
    });
  }

  public subscribe(topics: string | string[]) {
    const topicArray = Array.isArray(topics) ? topics : [topics];
    topicArray.forEach((t) => this.subscribedTopics.add(t));

    if (this.socket?.connected) {
      this.socket.emit('message', {
        action: 'subscribe',
        topics: topicArray,
      });
    }
  }

  public unsubscribe(topics: string | string[]) {
    const topicArray = Array.isArray(topics) ? topics : [topics];
    topicArray.forEach((t) => this.subscribedTopics.delete(t));

    if (this.socket?.connected) {
      this.socket.emit('message', {
        action: 'unsubscribe',
        topics: topicArray,
      });
    }
  }

  public on(event: string, callback: SocketEventListener) {
    if (!this.listeners.has(event)) {
      this.listeners.set(event, new Set());
    }
    this.listeners.get(event)!.add(callback);

    // Also register on underlying socket instance
    this.socket?.on(event, callback);

    return () => {
      this.listeners.get(event)?.delete(callback);
      this.socket?.off(event, callback);
    };
  }

  public disconnect() {
    if (this.authTimeoutTimer) clearTimeout(this.authTimeoutTimer);
    this.subscribedTopics.clear();
    this.listeners.clear();
    this.socket?.disconnect();
    this.socket = null;
  }
}

export const wsManager = new WebSocketManager();
